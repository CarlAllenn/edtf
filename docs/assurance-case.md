# Security assurance case

Why this project's security requirements are met: the threat model, the
trust boundaries, the design argument, and the argument that common
implementation weaknesses are countered. The security requirements
themselves — what a user can and cannot expect — are stated in
[SECURITY.md](../SECURITY.md); this document is the evidence that they
hold.

## Threat model

The software parses attacker-controlled text and ships through a supply
chain. The threats, in order of exposure:

1. **Hostile input.** Every entry point (`edtf-core` parse, the
   normaliser, the CLI, the wasm bindings, the SQL functions) accepts
   arbitrary strings, potentially from unauthenticated users of a
   downstream application. The feared outcomes are panics or
   non-termination inside a host process — a Postgres backend, a browser
   tab, a server — and incorrect verdicts that corrupt downstream data.
2. **Supply-chain substitution.** A consumer fetching a crate, npm
   package, tarball, binary or image receives bytes other than what CI
   built — through registry compromise, release-asset tampering, or a
   publish pipeline that signs the wrong thing.
3. **Build/CI compromise.** A poisoned dependency, action, or cache
   causes the pipeline itself to produce and attest malicious artifacts.
4. **Privilege escalation via the extension.** `edtf_postgres` is
   `trusted = true`: non-superusers can install it, so any memory-safety
   defect in it runs inside a database backend.

Out of scope: denial of service by volume (rate limiting is the host's
job), confidentiality (the library holds no secrets and processes no
personal data of its own), and the security of the Postgres server or
browser hosting the code.

## Trust boundaries

- **The input string** is the primary boundary: everything after
  `parse()` is typed, validated data; everything before it is untrusted
  bytes. All downstream crates construct values through `edtf-core`'s
  model, so outputs are valid by construction — there is no code path
  that emits an EDTF string that does not re-parse.
- **The process boundary** around each deployment shape: the extension
  inside a Postgres backend, the wasm module inside a browser sandbox,
  the CLI as an ordinary process. The core is `#![no_std]` with no
  filesystem, network or clock access, so the parser cannot cross this
  boundary even in principle.
- **The publish boundary**: what CI builds versus what registries and
  releases serve. Everything a consumer can fetch is compared
  byte-for-byte against what the tagged run built before anything is
  attested (`verify-registry-bytes.sh`), and attestation happens last,
  only on proof.

## Secure design principles

- **Economy of mechanism / minimised attack surface**: the core is one
  zero-dependency `no_std` crate; `unsafe_code = "forbid"` at the
  workspace level, so the entire parsing surface is safe Rust and
  memory-safety failures are excluded by construction, not by review.
- **Fail-safe defaults**: parsing fails closed — anything not grammatical
  per the Annex A reading is rejected with an error offset, never
  coerced. The normaliser refuses to guess: ambiguous input returns every
  reading, impossible dates poison the whole input.
- **Complete mediation**: there is exactly one parser; the CLI, wasm,
  Postgres and normaliser layers all go through it, so there is no
  secondary grammar to drift.
- **Least privilege**: CI jobs run with per-job minimal token
  permissions, `egress-policy: block` allowlists, and no long-lived
  registry secrets (OIDC trusted publishing). The publish workflow
  carries no cache of any kind.
- **Honesty as a design rule**: three-valued temporal relations never
  collapse "possible" into "definite"; bounds are total; the enumeration
  API refuses to enumerate the unenumerable rather than truncating.

## Common implementation weaknesses, countered

- **Memory safety** (buffer overflows, use-after-free, CWE-119 class):
  excluded by safe Rust with `unsafe` forbidden; the only unsafe code in
  any shipped artifact is generated by pgrx's audited bindings.
- **Panics / crashes on input** (CWE-248): continuously fuzzed —
  coverage-guided libFuzzer targets run nightly in CI with a shared
  corpus, plus in-tree never-panic property tests over random bytes,
  mutated valid inputs and grammar soup. A reproducible panic on any
  input is treated as a security bug (SECURITY.md).
- **Non-termination** (CWE-835): the grammar is non-recursive and input
  length is the loop bound; the same fuzzers would surface hangs as
  timeouts.
- **Injection-class defects** (CWE-89 and friends): the SQL surface takes
  `text` arguments through Postgres's typed function interface; nothing
  interpolates strings into queries. The extension performs no I/O.
- **Known-vulnerable dependencies** (CWE-1104): cargo-deny advisories
  gate every commit; Renovate proposes updates continuously with a
  seven-day cooling-off; the one accepted advisory (RUSTSEC-2021-0127,
  an unmaintained-crate notice reached only via pgrx) is pinned to a
  documented ignore that fails the build if it goes stale.
- **Static analysis**: clippy at `all` + `pedantic` with warnings as
  errors on every commit, and CodeQL (Rust and Actions packs) on every
  pull request and weekly on `main`.
- **Supply-chain weaknesses**: SHA-pinned actions, hash-verified
  toolchain downloads, lockfile-pinned tools with provenance
  verification (mise `locked` mode), harden-runner egress blocking,
  signed commits, immutable tags and releases, and Sigstore attestations
  covering every published artifact — published both in GitHub's
  attestation store and as `*.intoto.jsonl` release assets.

## Why this is believed sufficient

The residual risks are logic errors in spec interpretation (mitigated by
the D-decision register, the shared conformance corpus, the legacy-oracle
fixtures and property tests, but never provably absent) and compromise of
the maintainer's accounts (mitigated by 2FA, signed commits and the
verification steps above). Both are documented rather than hidden, and
both fail toward detectability: wrong bytes fail verification, and wrong
verdicts are reproducible test cases.
